# Crawldad — Threat model & security boundary

Crawldad is a hosted, multi-tenant service that drives customer-supplied browsers against arbitrary sites and records the result. The assets it must protect are: **provider/backend credentials**, **form-fill secrets**, **tenant API keys**, **extracted PII and screenshots**, and **cross-tenant isolation**. This document states the boundary as built and verified against the code; it is terse and factual. It cross-references the engine contract ([`SPEC.md`](SPEC.md)), the HTTP surface ([`API.md`](API.md)), and the payload language ([`PAYLOAD_SPEC.md`](PAYLOAD_SPEC.md)).

---

## Credentials by reference

Payloads and events never carry a raw secret. A backend binding carries a **`credentialRef`** — a name resolved to a live secret **only at connect time**, tenant-scoped, living solely in the interpreter's memory for that session. A tenant registers its browser connect credentials through the API (`PUT /browsers/{name}`, `Features/Browsers/`); the registered name is the `credentialRef`, and the secret is **encrypted at rest** (ASP.NET Data Protection, purpose-bound) in a tenant-partitioned Marten document — never returned by any endpoint, and never written to an event or log. `apiKey` mode registers a provider api key; `connectUrl` mode registers the whole connect URL, treated as a one-time secret (still scrubbed). (In the Azure deployment the Data-Protection key ring is persisted: the whole ring is stored in a dedicated blob and each key is wrapped by a Key Vault key, both reached passwordless via the app's managed identity — so stored credentials survive a container redeploy, including scale-to-zero on staging. Config-gated by `Crawldad:DataProtection` (blob URI + key id); absent that config the host keeps the framework's default local key ring, so dev/test are untouched. See ARCHITECTURE.md B.5 and issue #65.)

Connect resolution (`IConnectCredentialResolver`) is **tenant-scoped by construction**: a `credentialRef` resolves against (a) the tenant's registered browsers first, then (b) a tenant-namespaced config fallback (`Secrets:{tenant}:{ref}`, an operator-seeded credential under the same tenant) — mirroring the form-fill path. There is **no** flat, process-global `Secrets:{ref}` lookup for connect credentials: a tenant can only ever resolve its own references, and a ref that belongs to another tenant (or to nobody) yields the same classified `secret-not-found` miss with no existence oracle — closing the multi-tenancy gap (#61). The form-fill vault remains a **keyed-adapter registry** (`ISecretStoreRegistry`, the same pattern as browser backends and storage sinks): `config` ships today; a real `azure-keyvault`/`aws-secretsmanager`/`hashicorp-vault`/customer-HTTP adapter is one registration line with no change to the interpreter.

**Webhook signing secrets** (`Features/Webhooks/`, issue #12) follow the same discipline: a tenant's registered webhook endpoint stores its caller-supplied HMAC secret as purpose-bound Data-Protection ciphertext in a tenant-partitioned Marten document, decrypted only in memory to sign an outbound delivery — **never returned by any endpoint** (rotated by re-registering), and never written to an event or log. The delivery body derives from already-scrubbed run state and carries **refs + metadata only** (never `result`/`partial`), so a webhook leaks no bulk PII; the HMAC signature it sends is derived, not secret. The outbound target is **SSRF-guarded in two layers**. At **registration** (`WebhookUrlPolicy`) the URL must be `https` and must not be a loopback, link-local, RFC 1918 / CGNAT / unique-local, unspecified, multicast, or any other IANA special-use **literal** (TEST-NET, benchmarking, IETF protocol-assignment, 6to4-relay anycast, Teredo, documentation), nor the Azure platform magic IP (`168.63.129.16`) — a fast first-line reject. Because a DNS name is accepted unresolved there, the authoritative check is at **send time** (`WebhookConnectGuard`): the delivery client resolves the target host, re-classifies **every** resolved address against the same reserved-range denylist (re-judging the embedded IPv4 of a NAT64 — the well-known `64:ff9b::/96` or the RFC 8215 local-use `64:ff9b:1::/48` — 6to4, or IPv4-compatible address, so a DNS64-synthesised `64:ff9b::169.254.169.254` cannot smuggle one through; a platform running NAT64 on an operator-specific network-specific prefix would need that prefix added to the denylist — a known limitation), and **pins** the connection to a validated address — so a name that points, or later **rebinds**, to the platform's own network is refused before any byte is sent and cannot be swapped for an internal address between the check and the connect. The client also **refuses redirects** (a 3xx to an internal target would otherwise bypass the guard) and connects **directly** with the proxy disabled — with a proxy the pinning would validate the proxy while the proxy resolved and reached the tenant host. With delivery on an independent durable channel, a hostile or unreachable receiver can neither reach the platform's own network nor affect run execution.

## Provider connect strings are not safe to leak

Both managed backends' connect strings are live-session or account credentials, and both are scrubbed:

- **Browserbase.** The account `apiKey` (`bb_live_…`) travels only in the `X-BB-API-Key` header of the session-create call, never in a URL. The returned `connectUrl` is `wss://connect.<region>.browserbase.com/?signingKey=<JWT>` — a **per-session** JWT, not the account key. Leaking it compromises that one session (until expiry), not the account; it is still not safe to leak.
- **Browserless.** The connect URL is `wss://production-<region>.browserless.io/chromium/playwright?token=<token>`; the `token` is **account-scoped** — a leaked token drains the account's balance.

## The scrubbing primitive

`Infrastructure/Security/CredentialScrubber.cs` is the single scrubber every sink funnels outbound text through. It is idempotent and a no-op on ordinary text (the word "token" without `=value` is untouched, so credential-free output is byte-identical to its golden). Two rules:

1. **Exact secret** — any credential resolved for the current run (registered into the per-run scope by the connecting adapter or by a `fill.secret`) is replaced wherever it appears, catching free-form text no param rule would recognise (a `log` echoing an input, an exception, a scraped page, a form value read back after a fill). Connect credentials are scrubbed only at length ≥ 8; a form-fill secret — user-chosen and possibly short (a PIN) — is scrubbed at a lower floor of 4 (a 1–3 char "secret" stays inert, a documented over-redaction guard).
2. **Known credential params** — on every **leak-prone channel** (logs, trace/timeline events, errors) the values of `apiKey`, `token`, and `signingKey` (case-insensitive) are redacted wherever they appear as `name=value`, covering a `ws://`/`wss://` query and a JSON-embedded connect URL. The value runs to a query/prose delimiter and excludes brackets, so the marker itself is inert (double-scrub is stable). Surrounding text (scheme, host, path) is preserved so the redaction stays diagnostic. **This rule is deliberately _not_ applied to a run's `result`/`partial`, nor to the durable resume checkpoint (cursor + var snapshot) a resumed run restores back into that content** — the customer's own extracted state, where a scraped WebForms href routinely carries a `token=`-shaped param: rewriting it to `[redacted]` would silently corrupt the data the caller asked for and is indistinguishable from the site actually serving `[redacted]` (issue #70), and a redacted cursor URL would additionally break the resume re-navigation (issue #82). Both go through `ScrubJson`, the shared JSON-channel scrubber. Exact-secret scrubbing (rule 1) stays unconditional there, so a registered credential echoed into a result or snapshotted into a checkpoint is still redacted; the capture channel bypasses this rule for the same reason (#78).

The redaction marker is `[redacted]`. A third input feeds the exact-match rule: the configured **tenant API keys** are registered as always-on (process-wide) secrets, so a leaked key is redacted anywhere it might surface — defence in depth, not a substitute for never emitting it.

## The per-run secret registry

`IRunSecretScope` (`AmbientRunSecretScope`) is opened at the run's **execution** entry — inline in `POST /runs` for a synchronous run, and by the background executor for an async run, where it spans the whole execution including retries and a checkpoint resume (a fresh `ConnectAsync` re-registers the resolved credential naturally, so a resumed run rebuilds its scrub set with no persisted secret). The scope is ambient (`AsyncLocal`), so it flows down the run's async call chain, concurrent runs never see one another's secrets, and **no secret outlives its run** — disposing the scope at run end clears the registered secrets, and the scrubber holds only a reference to the seam, never a secret.

## What is scrubbed, and where — one chokepoint per sink

| Sink | Chokepoint | Note |
|---|---|---|
| **Connect exceptions** | the real adapters | any provider fault becomes a hand-written, secret-free `BrowserConnectException`; the raw `wss://…?token=` URL is never wrapped in. |
| **Marten events** | `RunEventScrubber`, at both append paths (the sync `POST /runs` append and the executor's own-session append) | every event is scrubbed before append; a `fill.secret` `Filled` event carries `secret:<refName>`, never the typed secret. |
| **Payload scripts** | `PayloadScript.Scrub` at save | a payload's script *is* the stored artifact, so it is scrubbed before the `PayloadDrafted`/`PayloadRevised` event is built and hashed — the immutable store can never receive a credential. |
| **Projections** | by construction | the `Run` snapshot, `RunTimeline`, and `PayloadSummary` derive purely from already-scrubbed events and add no un-scrubbed field. |
| **Logs** | `ScrubbingLoggerFactory` (decorates `ILoggerFactory` in host configuration) | every category — application, Wolverine, Marten, ASP.NET — scrubs its rendered message before any sink writes it. Central, not per-call-site. |
| **HTTP response** | `StartRunEndpoint` (sync) / `RunFinalization` (async — scrub-before-store into `RunProgress`) | the failure message is scrubbed by both rules; the shaped `result`/`partial` are exact-secret scrubbed via `ScrubJson`, which **skips the credential-param rule** so caller-extracted page content is returned verbatim — a registered secret echoed into a result is still redacted by exact match (issue #70). The async poll (`GetRunEndpoint`) then serves the already-scrubbed `RunProgress`. |
| **SSE frames** | `RunEventsEndpoint` | each frame re-serialises the already-scrubbed persisted event; the durable stream (not an in-memory buffer) is the frame source. |
| **Timeline** | by construction | folds the already-scrubbed step trace; surfaces refs, never raw values. |
| **Screenshot blobs** | `IScreenshotStore` (content-addressed ref) | the immutable event holds only a `screenshots/{sha256}.png` ref; the image lives in a deletable, tenant-partitioned, TTL-governed store. |

**The one thing text-scrubbing cannot cover:** a screenshot captures the page as *pixels*, so a shot taken right after a `fill.secret` can show the typed value on-screen. Mitigations are structural, not textual: the ref-only immutable trace, the shorter 7-day screenshot TTL (auto-expired by the janitor), and per-tenant partitioning. Authors must not place a `screenshot` where a secret is rendered on-screen; the platform never routes the bytes anywhere but the deletable store.

## Durable state at rest

The background executor leaves run state in three durable stores beyond the immutable trace. The invariant that holds across all of them: **inputs travel by reference**, so a `credentialRef` — not a resolved secret — is what they contain.

| At-rest store | Holds | Scrubbed? | Retention |
|---|---|---|---|
| `RunProgress` | the pollable `result`/`partial`/`failure` body and the durable checkpoint (cursor + accumulated-var snapshot) | **yes** — scrubbed before store (the `result`/`partial` and the checkpoint cursor/var snapshot both via `ScrubJson`: exact-secret redaction, param-rule-exempt, so a resumed var/cursor isn't corrupted — #70, #82); extracted PII it holds lives here (deletable), never in an event | **TTL-swept** (the result/partial body nulled past `ResultTtl`, default 7 days, leaving a pollable `resultExpiredAt` marker) **and on-demand erasable** (`DELETE /runs/{id}` — see below); a mutable, executor-owned document |
| `RunExecutorSaga` | the run's `script` + `inputs` — the resume source | inputs are caller config; credentials among them are refs | **reclaimed atomically at terminal**: the finaliser deletes the saga in the same transaction as the run's terminal disposition (`RunFinalization` → `session.Delete`), so a finished run's inputs+script are gone the instant it reaches terminal — no separate cleanup step to lose, no crash window. A non-finalised run keeps its saga (the resume source). |
| Wolverine envelopes | `StartRun` carries `script`+`inputs`; `ExecuteRun`/`RunDeadline` carry only the run id | inputs are refs | handled envelopes retained until Wolverine's sweep; a scheduled `RunDeadline` sits until its delay fires. |

The honest corollary: a raw secret passed as a **plain input value** would sit un-scrubbed in the `inputs` carried by `StartRun` and the saga (the scrubber redacts registered run secrets and credential-shaped params, not arbitrary values). That is exactly why form-fill credentials must be a `secretRef` type, kept out of the run's eval scope entirely, never a plain input.

## Durable blob storage, retention & PII erasure

Bulk extracted downloads and failure/explicit screenshots never enter the immutable event store — events carry metadata only (content id, hash, blob ref); the bytes live in **deletable blob storage**, config-selected via `Crawldad:Storage:Provider` (`filesystem` default, `azure`, or the in-memory `fake` for tests).

- **Tenant partitioning.** Every blob is stored under its tenant (`{Root}/{tenant}/…` on disk, a `{tenant}/…` prefix in the Azure container); the idempotency probe resolves a tenant-qualified location, so one tenant can neither read, overwrite, nor probe another's blob by content id. The content-id/screenshot ref handed back to the engine stays tenant-independent, so the wire result and trace are byte-identical across providers. The one attacker-influenceable path segment (the tenant, from the authenticated principal) is guarded against traversal; the content id (a GUID) and screenshot key (a hex digest) are intrinsically safe.
- **Retention.** A host-enforced policy (`Crawldad:Storage:Retention`), so it applies uniformly across filesystem and Azure. A scheduled `RetentionJanitor` background service sweeps on `SweepInterval` (default 1 hour, must be positive): it deletes blobs past their category TTL — **downloads 30 days, screenshots 7 days** (shorter, because a screenshot can show PII) — and drives the non-blob `IRetentionSweep` sweeps on the same cadence, the run-result sweep nulling an async run's stored `RunProgress` result/partial body past **`ResultTtl` (default 7 days**, the PII-grade window, since the sync path never persists a result). A TTL of 0 retains that category indefinitely; `Retention:Enabled=false` disables the janitor. A non-positive sweep interval, or a durable provider missing its target, fails the host loudly at boot. One asymmetry: the result sweep enumerates **configured** tenants (conjoined tenancy needs a tenant to scope each session, as `RunRecoveryService` does), so a tenant removed from `Crawldad:Tenants` is no longer swept and its stored results are orphaned — unlike blobs, enumerated physically across all tenants; de-provisioning a tenant must erase its results out of band.
- **Erasure — on-demand + TTL.** Two erasure paths ship. **(1) TTL auto-expiry.** The janitor is the *sole* caller of `IRetentionStore.DeleteAsync` (a blob removed once past its category TTL) and it drives the parallel `IRetentionSweep`s — the run-result sweep nulls a stored `RunProgress` result/partial body past `ResultTtl`, stamping a `resultExpiredAt` marker while the terminal status/stats stay pollable (a coherent shape, not a surprise 404). **(2) On-demand right-to-erasure.** `DELETE /runs/{id}` (tenant-scoped, authenticated) hard-deletes a **finished** run's `RunProgress`, its `Run`/`RunTimeline` read models, and its **event stream** in one transaction — the bulk result body *and* the incidental PII a scrubbed timeline still holds (a `LogEmitted` message, a `Navigated` URL). It refuses a still-active run (`409 run_still_active` — cancel it first) and is idempotent (`204` then `404`). Still future work: **blob-level** on-demand erasure (delete a subject's matching download/screenshot blobs — `DeleteAsync` is the primitive it would build on) and optional **crypto-shredding** (encrypt each blob under a per-run/subject key; discard the key to render it unrecoverable). The shipped guarantees are TTL expiry + per-tenant partitioning + the ref-only trace for blobs, and both TTL expiry and `DELETE`-based erasure for run results.

## Authentication & tenant isolation

Every route requires an authenticated tenant except four deliberately anonymous, tenant-independent artifacts — `GET /health`, `GET /schema/crawldad-1.schema.json`, `GET /llms.txt`, `GET /openapi.json`. An endpoint-enumeration test discovers the live route table and asserts every other route rejects an unauthenticated request, so a route added later without auth fails the test by default.

- **Mechanism.** Per-tenant API keys presented as `Authorization: Bearer <key>` (checked first) or `X-Api-Key: <key>`, validated by a custom ASP.NET authentication handler against a config-bound tenant directory (`Crawldad:Tenants` → `{id, apiKey, actor}`). A missing or unknown key is `401`, and the key is never echoed or logged.
- **Keys are hash-compared.** `TenantRegistry` keeps only a SHA-256 of each configured key (never plaintext) and compares with `CryptographicOperations.FixedTimeEquals`, probing the **whole** set with no early return — so neither the match position nor a near-miss leaks through timing. Boot-time guards reject a missing id/actor, an API key shorter than 16 characters, a duplicate id, a reused key, and a `:` in a tenant id (which would make the per-tenant vault-key prefix `Secrets:{tenant}:{ref}` ambiguous).
- **Actor from the principal, never the body.** Payload mutation events carry a `by` actor stamped from the authenticated tenant's configured identity; the request contracts have no `by` field to spoof. On the **console** path (below) the same `by` is the authenticated human's **email**, so attribution follows the channel — a console write's event history carries the human, a key write's carries the tenant actor.
- **A second, config-gated console scheme (`ConsolePrincipal`; issue #119).** Alongside the default `ApiKey` scheme the API can validate the portal's first-party Entra token and map it to a tenant via its own **membership store** (tenant ↔ verified email ↔ role). It is a **non-default** scheme registered **only when `Crawldad:ConsoleAuth` is configured** (the operator runbook, `docs/CONSOLE_AUTH_RUNBOOK.md`) — **off in every live environment today**, so the statements above are unchanged until an operator activates it. When active, an explicitly **enumerated** set of endpoints (`ConsoleReadEndpoints` GETs + `ConsoleWriteEndpoints` writes) opts into a `ConsoleOrKey` policy that additionally accepts a console principal; **every other route stays `ApiKey`-only**, and the enumeration is pinned by a test (reads and writes as separate lists) so scope creep fails CI. A console token with no active membership stamps no tenant claim → `403`; a request presenting **both** a console token and an API key is rejected, never merged. Console **writes** additionally pass a guard that appends a lightweight **audit** row (tenant, actor email, HTTP operation, route template, status, timestamp — no bodies, no secrets) and enforces a generous per-`(email, tenant)` **sliding-window rate limit** (`429` over the limit) — abuse insurance keyed on the human, never the shared portal identity. **The membership `role` is enforced, not merely stamped (issue #119 PR6).** Key management (`/tenant/keys` mint/rotate/revoke) and membership management (`/tenant/memberships` add/remove/change-role) require an **Owner** on the console channel — a stricter `ConsoleOwnerOrKey` policy that is **fail-closed** (a Member, or a missing/unknown role, is a `403`); every read and every operational write (replay, payload save/revise, webhook register/delete, billing session) stays **Member**-reachable. An **API-key** caller is unaffected — key possession is full tenant authority, ungated by role. A user may hold memberships across multiple **workspaces** (the customer-facing name for a tenant); the portal shell switches between them, each request scoped to the active one, and the API's membership store — never a request parameter — decides which tenants a user may act as.
- **Tenancy model.** Marten conjoined multi-tenancy: one shared schema, every stream and document row qualified by `tenant_id`, every session opened for a tenant. A cross-tenant read returns nothing → **`404` (not `403`)**, so a tenant cannot even confirm another's resource exists. The tenant flows into **every** session, including the out-of-request ones: the background executor reads `Envelope.TenantId` (a run with no tenant fails closed), checkpoint resume and SSE backfill open tenant-scoped sessions, startup recovery fans out over every configured tenant, and the async projection daemon projects each event under its own tenant. Backend **connect credentials** resolve tenant-scoped (a tenant's registered browsers, then `Secrets:{tenant}:{ref}`) — no process-global credential namespace (#61); backend sessions are per-run and never shared across tenants; storage is partitioned per tenant.
- **Upgrade path.** Conjoined tenancy is one database with no per-tenant provisioning; a stronger schema-per-tenant or database-per-tenant posture is available later via Marten with no change to the endpoints or executor — only the store wiring.

## Payload safety & resource limits

The payload language is the first line of defence: it cannot `eval`, cannot reach the filesystem/network, and cannot loop unbounded (every loop carries a mandatory cap), so a schema-valid, save-validated payload has a **bounded, inspectable effect surface** ([`PAYLOAD_SPEC.md`](PAYLOAD_SPEC.md)). Backing that, five server-side resource caps a payload can never raise bound a run's cost and blast radius — max steps, max downloaded bytes, max events, an expression fuel budget, and per-tenant concurrent runs (with a durable admission queue rather than rejection) — specified with their defaults in [`SPEC.md`](SPEC.md#resource-limits) and [`API.md` §12.4](API.md).

An unbounded synchronous connection is itself a connection-holding DoS vector; the 120 s sync cap with auto-upgrade (see [`ARCHITECTURE.md`](ARCHITECTURE.md#a5-run-lifecycle)) closes it while keeping the credential-scrubbing boundary intact across the request→background handoff — the run's ambient secret scope stays open until background finalisation, so an upgraded run's events and result are scrubbed exactly as an inline run's.

## DB-backed tenant registry & API keys

The configured `Crawldad:Tenants` directory (above) is joined by a **DB-backed tenant registry**: tenants and their API keys stored as Marten documents, administered by the interim management API ([`API.md` §20](API.md)). It is additive — a presented key resolves against the registry first and **falls back** to the configured tenants, so the config-bound guarantees above still hold for env tenants.

- **Keys are stored hashed, never encrypted, never in plaintext.** A registry API key is `ck_<env>_<random>` with 256 bits of CSPRNG entropy; only its **SHA-256** (plus a short non-secret display prefix) is persisted. The raw key is returned **once** at issue and never stored, evented, or logged. A plain (unsalted) SHA-256 is sufficient precisely because the key is high-entropy and server-minted — there is no low-entropy password to brute-force or rainbow-table, so a per-key salt buys nothing; this is the same reason the SPEC permits SHA-256 for these keys. (Registry keys are therefore **not** in the credential-scrubber's always-on set — that set needs plaintext, which the registry deliberately never holds; the raw key exists only in transit in the one-time issue response.) Resolution matches the SHA-256 of the presented key against the stored hash.
- **Suspension & revocation are fail-closed and prompt.** A key resolves only while it is non-revoked **and** its tenant is `active`; a suspended tenant or a revoked key is rejected as `401`, indistinguishable from an unknown key (no existence oracle, mirroring the `404`-not-`403` stance). Resolutions are cached with a **short TTL** to keep the auth path off the database; a revoke or suspend **invalidates the cache in-process immediately** on the serving instance, and the short TTL bounds staleness on any other instance. Negative lookups are deliberately **not** cached, so a flood of junk keys cannot grow the cache.
- **The management key is a scoped operator credential.** The management API authenticates with a **single** `Management:ApiKey`, compared in **constant time** (both sides hashed to a fixed-length digest before `FixedTimeEquals`, so neither length nor match-prefix leaks), presented as a bearer token — never a tenant key, and never mixed into the tenant auth path. Its scope is administrative: it can create tenants and mint/revoke keys for **any** tenant, so it is a high-value secret to be injected from a secret store, rotated out of band, and kept off any tenant-reachable surface. When **unconfigured the management surface is unmapped entirely** (`404`), so a deployment that does not opt in exposes no administrative attack surface at all. This is an interim posture until portal operator auth (per-operator identity, audit, least-privilege) supersedes the single shared key.
- **Registry documents are single-tenanted by necessity.** The tenant + key documents *define* tenants, so they cannot themselves be conjoined-tenant-scoped; they are stored single-tenanted and queried before any tenant scope is established (the one place the tenant boundary is legitimately crossed — to establish it). They carry no tenant payload data, only registry identity and key hashes. The console **membership** documents (tenant ↔ verified email ↔ role, issue #119) and the console-write **audit** rows are single-tenanted for the same reason; memberships hold portal identity (a normalized email), never a credential, and a tenant's last active **Owner** membership can never be removed **or downgraded** (the anti-orphan invariant, enforced atomically under the per-tenant advisory lock). Membership management (add / remove / change-role, issue #119 PR6) is **Owner-only** on the console channel, and an active `(tenant, email)` pair is unique — a partial unique index plus the store-level lock make two concurrent attaches converge on one row.
- **Self-service key management is strictly self-scoped, and last-key revocation is guarded.** A tenant manages its **own** keys with its own key (`/tenant/keys`, [`API.md` §22](API.md)); the tenant comes only from the principal, so a caller can act only on itself, and a foreign/unknown id is a `404` with no existence oracle. The key authenticating the request is never revocable (rotate instead). Revoking the tenant's **last active key** is allowed only when a **console recovery path** exists — a registry tenant with ≥1 active Owner membership, so a human can still reach the workspace through the portal after every key is gone; a tenant with no membership keeps refuse-last-key. The last-active and last-Owner guards are enforced **atomically** under a per-tenant advisory lock (with optimistic concurrency on the membership document), so two concurrent revokes can never both empty the set.
- **Recovery/retention fan-out is env-only (a known limitation with a PII backstop).** Startup run-recovery and the result-retention sweep still enumerate only the env-configured `Crawldad:Tenants` (they fan out over `TenantRegistry.TenantIds`), so a **registry-only** tenant's interrupted runs are not auto-resumed and its aged result bodies are not swept on the timed sweep — the same "configured tenants only" limitation already documented for de-provisioned tenants. This does **not** weaken the erasure guarantee: on-demand right-to-erasure (`DELETE /runs/{id}`, which hard-deletes the result, read models, and event stream) is tenant-scoped and works for a registry tenant exactly as for a configured one, so it remains the backstop for a departing registry tenant's data until the fan-out is extended to active registry tenants.

## The portal (Crawldad.Portal) — surface & assets

`Crawldad.Portal` is the customer-facing web console shipped this launch (the P1–P4 phases of issue #119). It is a self-contained **Blazor Web App** that **does not reference the API project** and reaches Crawldad **only** through the typed `Crawldad.Client` SDK over HTTP (`PortalHost`; the SDK-only rule is review-enforced by #119 — the portal never touches the API's Marten schemas directly). Every page renders **static server-side (SSR)** except one, which runs Interactive Server; there is **no WebAssembly** at all, which is the structural reason a tenant API key never has to reach the browser (#119). The portal's own Marten document store lives in the **`portal` schema** on the **same** Postgres instance as the API, fully isolated by `DatabaseSchemaName` from the API's `crawldad` schema (`PortalHost.AddCrawldadPortal`).

The portal introduces three assets of its own; every other asset in this document (provider credentials, form-fill secrets, extracted PII, screenshots) stays an **API** asset that the portal only ever views **by reference** through the tenant's key:

- **The tenant's Crawldad API key**, held at rest as `PortalTenantLink.ProtectedApiKey` — ASP.NET **Data-Protection ciphertext**, purpose-bound to `Crawldad.Portal.Auth.TenantApiKey.v1` (`PortalTenancy.ApiKeyProtectorPurpose`, pinned so `Unprotect` cannot be broken by a namespace rename). The raw key is never stored, logged, evented, or rendered to the browser. **In console-mode (issue #119 PR5) this asset is optional**: the attach flow verifies the key, records the membership, and **discards** the key, so a console-mode link carries `ProtectedApiKey = null` — no stored per-tenant credential at rest. A stored key remains only for the stored-key (unconfigured) mode and, transiently, as a read-fallback until a console-mode redeploy retires it.
- **The portal session** — a cookie (`crawldad.portal.auth`, `HttpOnly`, `SameSite=Lax`, `Secure=Always` outside dev, 7-day sliding) whose principal carries **only identity claims** (email, name); the tenant key is never part of it (`PortalHost.AddCookieAuthentication`, `PortalPrincipal`).
- **The account identity and its OTP challenges** — `PortalUser` (keyed by normalized email, created lazily on the first successful sign-in) and `OtpChallenge` (a **salted SHA-256 of the code only** — the plaintext is never persisted). No customer run data or PII lives in the `portal` schema; the portal store holds account identity plus the encrypted link, nothing more.

## The portal — trust boundaries

| Boundary | What crosses it | Control |
|---|---|---|
| **Browser ↔ portal** | the auth cookie, form posts, screenshot/SSE bytes | Cookie auth **without ASP.NET Identity** (the cookie handler directly). Every `/app/*` page is `[Authorize]`, so an unauthenticated request is a `302` to `/login` by the authorization middleware (`Routes.razor`); `UseAntiforgery()` guards the state-changing form POSTs (sign-in, sign-out, workspace link, payload save/revise, replay, billing). **The tenant API key never crosses this boundary** — SSR-only, no WASM (#119). |
| **Portal ↔ API** | every data read/write | Routed through a `CrawldadClient`, resolved once per request by `IPortalTenantContext` (and the circuit-safe `ICircuitTenantResolver`) via one shared decision so the two never drift. **Two modes (issue #119 PR5):** stored-key (unconfigured, byte-identical to launch) authenticates with the tenant's key, **decrypted in server memory only**; console-mode authenticates as the portal's **first-party console identity** (a short-lived Entra token + membership selectors), reads console-first with the stored key as a transition read-fallback, and **writes console-only** — a console-mode link needs no stored key at all. Either way, unauthenticated or unlinked resolves to a clean *not-linked* state (`null` / `NotLinkedException`), **never a client with an empty or absent credential**. |
| **Portal circuit memory** | the decrypted key on the one interactive page | The live-trace page (`/app/live/{runId}`, `@rendermode InteractiveServer`) resolves the tenant through the circuit-safe `ICircuitTenantResolver` (its `IHttpContextAccessor` is null on a circuit, so identity comes from `AuthenticationStateProvider`) and holds the tenant client **only in server-side circuit memory** — the key is never written to `PersistentComponentState`, a component parameter, or anything serialized to the browser (`CircuitTenantResolver`, `LiveTrace.razor`). Disposal cancels the SSE stream, so a closed tab leaks no connection. |
| **Portal schema in shared Postgres** | account identity, the encrypted link, OTP challenges | One `portal` schema, isolated by `DatabaseSchemaName` from the API's `crawldad`. Documents are keyed by portal-account email and hold **no** customer run data; the API's conjoined per-tenant data is unreachable from the portal's store — it is reached only through the tenant key, above. |

## The portal — passwordless email OTP

Sign-in issues a **6-character** code from an **unambiguous 31-symbol alphabet** (`OtpCodeGenerator` — uppercase letters and digits with `0/O/1/I/L` removed, ~4.95 bits/character → **~29.7 bits** over the code), drawn from a CSPRNG and delivered by `IEmailSender`. The code is persisted **only** as a **per-challenge salted SHA-256** (`OtpHasher`, `OtpChallenge` — the plaintext is never stored) and verified in **constant time** (`CryptographicOperations.FixedTimeEquals`, which also absorbs a length mismatch without leaking timing). A single-round hash is sufficient because the code is high-friction by **policy**, not by hash cost: a **10-minute** lifetime (`CodeLifetime`), **single use** (`Consumed`), a **5-attempt** cap per challenge (`MaxAttemptsPerChallenge`), and a **3-request / 15-minute** window per email (`MaxRequestsPerWindow` / `RateLimitWindow`). The attempt cap cannot be beaten by racing guesses: `OtpChallenge` is stored with **Marten optimistic concurrency**, so parallel verifies serialize on the document version and the cap is re-checked on each retry pass (`PortalHost`, `PortalAuthService.VerifyCodeAsync`). Sign-in is **enumeration-safe**: a challenge is created and "sent" for **every** address whether or not a `PortalUser` exists, the code is dispatched **before** the challenge row is persisted (a fail-closed sender throws first and leaves no orphan row), and the status copy is byte-identical for known and unknown addresses (`PortalAuthService.RequestCodeAsync`, `OtpMessages`). Cookie **issuance** (`HttpContext.SignInAsync`) happens only on the **static-SSR** login POST — never on an interactive circuit, whose `HttpContext` is null — and the post-sign-in return URL is open-redirect-guarded to **same-site absolute paths only** (`SafeRedirect.ToLocalOrApp`, which rejects absolute URLs, protocol-relative `//host`, the `/\host` variant, and a leading backslash; sign-out redirects via `Results.LocalRedirect`).

## The portal — the tenant API key at rest, and validate-before-store

A portal account is linked to the Crawldad tenant it acts as by a `PortalTenantLink` keyed by the **same** normalized email as the account (so link and account line up one-to-one). The account-area link path **validates the submitted key against the live API before persisting** (`WorkspaceLinker`): it probes `GET /tenant` with a one-shot client built for that key and writes **only** on success, storing the **authoritative** tenant id the key returns (never the entered casing). A rejected key (`401`), a key that authenticates a **different** tenant than the one entered, or an API that cannot be reached all store **nothing** — a wrong key can never be persisted. The submitted key is treated like a password throughout: never logged, echoed, or returned in a response.

**How the key is retained depends on the mode (issue #119 PR5).** In stored-key (unconfigured) mode the link holds the key **only** as the purpose-bound Data-Protection ciphertext above (`MartenPortalTenantLinkStore` protects on write; `PortalTenantContext` / `CircuitTenantResolver` unprotect it per request/circuit to build the client, and for nothing else). In **console-mode** the link path is **verify-then-discard**: it verifies the key, records the account's **Owner membership** on the API (the console authorization authority), and stores the link **without** the key (`ProtectedApiKey = null`) — so there is no per-tenant credential at rest, and the console credential authenticates from there on. If the membership cannot be recorded (an env tenant, or a transient fault) it falls back to storing the key, so a link attempt never locks the account out. This makes the stored key **unnecessary** in console-mode; the residual `PortalTenantLink`/Data-Protection machinery is retired in a small follow-up once staging has run console-mode.

## The portal — reading a tenant's data without exposing the key

Screenshots render as plain `<img>` tags pointing at a **same-origin, cookie-gated proxy** (`RunScreenshotProxy`, `GET /app/runs/{runId:guid}/screenshots/{reference}`, `RequireAuthorization()`): it resolves the signed-in tenant and **streams the PNG through their per-request `CrawldadClient`**, so the API key never reaches the browser; the bytes are marked `private, no-store` so no shared cache retains the page content; and an unlinked user or an unknown / foreign / expired ref is a **`404`** — never a cross-tenant leak and never a `500`. The ref rides a **single escaped path segment** in the SDK call (`Uri.EscapeDataString`, `CrawldadClient.GetRunScreenshotAsync`), so a traversal-shaped ref cannot collapse the path — the no-traversal guarantee is local, not left to server-side URL normalization (and the ref itself is a content-addressed hex digest, intrinsically safe). The **one interactive page**, the live-trace viewer, streams the run's SSE trace over its circuit through the tenant client and renders **already-scrubbed** frames verbatim (`LiveView.Preview` — the API scrubs every event before it is appended, so the portal re-displays scrubbed text and adds no un-scrubbed field), with the key staying on the server-side client as above.

## The portal — input secrecy: write-only replay vs preserved payload text

Two editor surfaces treat their text oppositely, on purpose. The **replay** form's resupplied inputs are **write-only**: a run's input *values* are never persisted (only redacted key *names* survive on the timeline), so a replay cannot recover them and the caller resupplies them — and the field is **cleared the instant it is submitted**, so a value that may carry a secret (e.g. a backend `credentialRef`) is never echoed back into the re-rendered form (`ReplayRunInput`, `RunDetail.ReplayAsync`). The **payload editor**'s script, by contrast, is **preserved** across a validation round-trip, because it is the artifact being edited and it is seeded from the **stored, credential-scrubbed** document (`PayloadEditorInput`, `PayloadDetail` — the script was already scrubbed at save by `PayloadScript.Scrub`, above), so re-rendering it can leak nothing a save did not already redact. The portal's only local check is JSON well-formedness; the authoritative crawldad-DSL validation runs server-side (`PayloadEditing`).

## The portal — billing surface

The portal's billing controls are two antiforgery-protected POST-then-redirect handlers (`BillingUiEndpoints`, `/app/billing/checkout` and `/app/billing/portal`): they resolve the tenant, ask the **API** — via the SDK — to mint a hosted-page URL, and redirect the browser to it; a not-linked account or an API error degrades to a **safe local redirect** (the account page, or an in-app "not yet available" result), never a `500`. **Nothing in the portal holds a Stripe or management key** — the portal carries no `Stripe:` or `Management:` configuration, and its container env is only `ASPNETCORE_ENVIRONMENT` plus the Marten connection string. The payment secrets and the plan-changing endpoint live in the **API**: `POST /billing/webhook` is the **public** provider endpoint (`[AllowAnonymous]` — the provider is not a tenant), authenticated by the event **signature**, and it is **verify-before-parse** — the raw body is read from `HttpContext` and handed to the gateway's `TryReadWebhookEvent` **before** any parse, so a bad signature changes nothing and is a `400` (`BillingWebhookEndpoint`). It is **anti-replay** (the first `IProcessedBillingEventStore.TryRecordAsync` for an event id wins; a redelivery is a benign `200`) and **registry-tenant-authoritative** (the tenant in the *verified* payload is the only thing that moves a tier). Unconfigured, it is **fail-closed**: the production `StripeBillingGateway` is a deliberate stub (the Stripe SDK is not yet a dependency), whose verifier **rejects every event** and whose session calls throw `BillingNotConfiguredException`, which the endpoints translate into a friendly "billing not yet available" — never a spoofed plan change, never a `500`. The line where the real `EventUtility.ConstructEvent` signature check plugs in is marked in `StripeBillingGateway`; the ordering guarantee (verify before parse, anti-replay, fail-closed) holds today regardless.

## The portal — threats & mitigations

| Threat | Mitigation & mechanism |
|---|---|
| Tenant API key exfiltrated to the browser | SSR-only, no WASM (#119); the key is decrypted in server memory and consumed to build the `CrawldadClient` — never in a cookie claim, `PersistentComponentState`, a component parameter, or the SSE/screenshot path (`IPortalTenantContext`, `CircuitTenantResolver`). |
| Key recovered at rest from the `portal` schema | Stored only as purpose-bound Data-Protection ciphertext (`PortalTenantLink.ProtectedApiKey`, purpose `…TenantApiKey.v1`); the raw key is never persisted, logged, or evented. |
| Account enumeration via sign-in | Identical behaviour and copy for known/unknown addresses; a challenge is created and sent for every address; send-before-persist (`PortalAuthService`, `OtpMessages`). |
| OTP brute force / guess-racing | ~29.7-bit code; 10-minute single-use lifetime; 5-attempt cap; 3-per-15-minute request cap; salted SHA-256 + `FixedTimeEquals`; cap made race-proof by Marten optimistic concurrency (`OtpHasher`, `PortalAuthService`). |
| Cross-tenant read of runs/screenshots | Every call carries the signed-in tenant's key; an unknown/foreign/expired ref is a `404`, not a leak; the proxy ref is escaped to one path segment (`RunScreenshotProxy`, `CrawldadClient`). |
| CSRF on a state-changing post | `UseAntiforgery()` over the form POSTs, including sign-out (`PortalHost`, `AuthEndpoints`, `BillingUiEndpoints`). |
| Open redirect after sign-in | Same-site-absolute-path-only guard; `LocalRedirect` on sign-out (`SafeRedirect`, `AuthEndpoints`). |
| A secret echoed back through an editor | Replay inputs are write-only (cleared on submit); the payload script is preserved only because it is already credential-scrubbed at save (`RunDetail`, `PayloadDetail`). |
| Spoofed plan change / webhook replay | Verify-before-parse by signature; anti-replay by event id; the fail-closed stub rejects all events when unconfigured (`BillingWebhookEndpoint`, `StripeBillingGateway`). |
| Unauthenticated access to `/app` | Every `/app/*` page is `[Authorize]`; a `302` to `/login` by the authorization middleware (`Routes.razor`). |

## The portal — explicitly accepted risks

- **Dedicated least-privilege portal identity** *(was: shared over-privileged deployment identity — resolved in issue #119 PR2).* The portal container app now runs under its **own** user-assigned managed identity (`id-crawldad-<env>-portal`), no longer the API/db-apply identity. That identity holds only what the portal actually reaches: *AcrPull*; *Key Vault Secrets User scoped to exactly the two secrets it reads* — the marten connection string and the Postmark token, **not** vault-wide, so it cannot read the API-only secrets (blob connection string, tenant/beta API keys); *Key Vault Crypto User scoped to only its own Data-Protection wrapping key* (`dataprotection-portal`); and *Storage Blob Data Contributor scoped to only its own key-ring container* (`infra/modules/{identity,registry,keyvault,storage,app}.bicep`). A portal compromise can therefore no longer read the API's vault, and the portal's ring keeps decrypting its stored links + auth/OTP cookies under the new identity. The **API/db-apply identity is untouched** and keeps its vault-scoped grants — it legitimately needs its own secrets and both Data-Protection keys; that broad footprint is the API's, not the portal's. (During cutover the shared identity's grant on the portal key-ring container is retained, so a rollback that repoints the portal app back to the shared identity needs no re-granting.)
- **First-party `ConsolePrincipal` console auth + a new Entra dependency (config-gated, off in every live environment; issue #119 PR2–PR5).** The API gained a second, **non-default** JwtBearer authentication scheme (`ConsolePrincipal`) that validates the portal UAMI's first-party Entra **v1.0** access token — issuer `https://sts.windows.net/<tenant>/`, signature from Entra's published JWKS, audience = the API App ID URI, and a **fail-closed** check for the `Console.Access` AppRole (`MapInboundClaims=false`; decision addendum #4 — an AppRole, centrally grant/revocable, not a mis-settable appid pin). It is **registered only when `Crawldad:ConsoleAuth` is configured** (the operator runbook, `docs/CONSOLE_AUTH_RUNBOOK.md`); **it is unconfigured in every live environment today**, so `ApiKey` remains the sole/default scheme and request handling is unchanged until an operator activates it. When active, an **enumerated** read set (PR4) and write set (PR5) opt into the `ConsoleOrKey` policy (pinned by a test as separate lists); every other route stays `ApiKey`-only; a console token with no membership is a `403`; both-credentials-at-once is rejected; and console **writes** are audited (human email + operation + route + status, no bodies/secrets) and rate-limited per `(email, tenant)`. The residual is the industry-normal first-party-console write scope: a portal compromise can, within the enumerated set and for a user with a membership, act as that tenant — mitigated by the enumeration, the human-email audit, the per-actor rate limit, and the fact that there is **no durable exfiltratable per-tenant credential at rest** (the token is short-lived, audience/AppRole-bound). Signing keys come **only** from Entra metadata: `ConsoleAuthOptions` exposes no key/issuer-override knob, so no production config value can inject a trusted key or issuer, and the CI harness swaps only the key *source* through a test-only options configurator unreachable from production config (the review's finding #8). **Full activation is still pending the operator runbook** (App Registration + AppRole assignment + the portal identity split).
- **Development-only ephemeral Data-Protection key ring.** Staging/production persist the portal's key ring durably — its own `dataprotection-portal` blob, each key wrapped by its own Key Vault key, application discriminator `crawldad-portal` so the portal and API rings cannot decrypt each other's payloads even if co-located (PR #142, mirroring the API's #65 module; half-configuration fails the boot). Development and tests keep the framework's default local ring (same posture as the API), where a lost ring only invalidates disposable dev links — the Account page renders a **re-link** prompt on `CryptographicException` rather than failing (nothing is silently mis-decrypted; `Unprotect` throws rather than returning garbage).
- **In-process cache invalidation only.** The portal holds **no** cross-request cache of its own (the link and identity are read fresh each request), but the plan/slot change its billing surface triggers invalidates the API's tenant-directory auth cache **in-process on the serving instance only** (`BillingWebhookEndpoint` → `TenantDirectory.InvalidateTenant`); other API replicas are bounded by that cache's short TTL (`TenantDirectory.CacheTtlSeconds`, 30 s). So a just-applied upgrade/downgrade — like a key revoke/suspend on the management path — takes effect immediately on one instance and within the TTL fleet-wide (the same posture the DB-backed registry section documents above).
- **Email provider is opt-in; unconfigured → fail-closed.** The production `IEmailSender` is `PostmarkEmailSender`, selected from `Crawldad:Portal:Email` (a Postmark server token + verified from-address) and used in **any** environment when configured. It delivers over Postmark's HTTP API and **throws** (`EmailDeliveryException`) on any non-2xx or transport failure — so it never silently succeeds — and logs only the HTTP status + Postmark error code (never the recipient, the token, or the code). **Until** the token is set, Staging/Production keep the `UnconfiguredEmailSender`, which **refuses to send** — never a silent success, never a logged code — so requesting a sign-in code surfaces an error rather than leaking one (`EmailModule`, `EmailSenders`, `PostmarkEmailSender`). A **half-configured** provider fails the boot (`ValidateOnStart`) rather than falling back silently. Deploying the shell before the token is set is deliberate (#119); end-to-end sign-in works once a Postmark server token + verified sender are configured.
- **Runtime schema auto-create for the `portal` schema.** The portal has no out-of-band `db-apply` command, and a normal start applies schema only in Development, so in staging/production it relies on **Marten's default runtime auto-create** (`AutoCreate.CreateOrUpdate`) on first document use (`PortalHost`, `infra/modules/app.bicep`) — the DB principal therefore needs DDL rights on the `portal` schema. The anonymous marketing `/` touches no database, so the app boots and serves before any schema exists (which is what the ingress probe and deploy smoke-test target).

## The portal — open items

- **Public signup / automated provisioning (#119 P5).** Self-service **key management** (issue / rotate / revoke) is **resolved** — it rides the tenant's own key at `/tenant/keys`, not the management surface (issue #119 PR3), and the portal drives it directly. What remains is **public signup**: automated free-tier tenant provisioning, which still needs a first-party portal→API provisioning path (the console identity, not the shared `Management:ApiKey` the portal deliberately does not hold). That provisioning endpoint and the signup flow are unbuilt; when they land they use the same first-party console identity as the console read/write path rather than a shared operator key.
- **Console-mode activation + the stored-key retirement follow-up.** The console auth path (reads/writes/audit/rate-limit) is built and config-gated **off** in every live environment; activating it needs the operator runbook (App Registration + AppRole assignment + the portal identity split). Once staging has run console-mode, a small follow-up deletes the now-unnecessary `PortalTenantLink.ProtectedApiKey` field, the Data-Protection `…TenantApiKey.v1` purpose, and the dev-seeder key path — the code paths already make the stored key unnecessary in console-mode; the field is kept only for the stored-key mode and the transition window until then.
- **Member invitation & invite abuse (issue #119 PR8).** Adding a member (`POST /tenant/memberships`, Owner-only) records the authorization edge, but there is **no invitation flow yet** — no email invite, no acceptance step, and an added Member can only reach the workspace once the console path is active and they sign in with that email. Rate-limiting and abuse controls on *inviting* (e.g. a stranger being spammed onto workspaces, or an Owner mass-adding emails) are a **PR8** concern, deferred until the invite UX lands; today the add is Owner-gated and audited, which bounds it but does not fully address invite abuse.
